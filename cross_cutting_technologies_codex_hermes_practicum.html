Codex и Hermes Agent: от установки до проверяемого результата

Настройте два агентных инструмента в отдельной учебной папке, сравните их с обычным чат-ботом, исследуйте границы доступа и поручите агенту проверить небольшой документ по явным критериям. В упражнении важны основания вывода, наблюдаемые действия и контроль человека; программировать не требуется.

Главный результат. Студент может показать, где запущен агент, какие файлы и внешние инструменты ему доступны, что именно он сделал и как проверить результат. Слова агента о прочитанном файле, отправленном сообщении или успешной проверке сами по себе не являются доказательством.

Карта практикума

  1. Подготовить искусственный проект и установить Codex CLI и Hermes Agent.
  2. Запустить Codex из каталога проекта, выполнить /init и проверить созданный AGENTS.md.
  3. Сравнить чат-бота и агента, а затем классифицировать локальные и MCP-доступы.
  4. На обезличенном учебном тексте выполнить две отдельные проверки: внутренней непротиворечивости и соответствия требованиям.
  5. Разобрать проблему установки или отказа доступа по наблюдаемым признакам, а не догадкам.
  6. Зафиксировать проект в частном GitHub-репозитории и проверить, что резервная копия действительно появилась.

Это практическое продолжение обсуждений 25–26.11.2026: ручной опыт с локальными агентами, доступом к файлам и внешним сервисам, сравнением Codex и Hermes, проверкой дипломной работы и сохранением истории проекта. Записи встреч содержат непроверенные фрагменты; таймкоды ниже относятся только к указанным локальным транскриптам и не доказывают, что вся встреча была просмотрена.

1. Что называют агентом

Чат-бот — интерфейс диалога; модель — компонент, который обрабатывает вход и генерирует ответ; агентная система — среда, где модель может выбирать и вызывать разрешённые инструменты, получать их результат и продолжать задачу. Модель сама по себе не является агентом. Чат-интерфейс с поиском остаётся чат-интерфейсом и одновременно может быть частью агентной системы. В упражнении сравниваются именно «чат без инструментов» и «агентная система с инструментом».

Кодинг-агент не обязан писать программу. Он может читать проект, составлять план, искать ошибки в нескольких связанных файлах, запускать разрешённые проверки и ждать следующего поручения. Отличие от обычного чата проверяется не названием, а тем, какие действия реально доступны и какие следы они оставляют.

Codex и Hermes — разные исполнительные среды вокруг моделей. В этом занятии Codex рассматривается как агентная среда, ориентированная на работу по задаче внутри проекта: контекст репозитория, инструкции AGENTS.md, инструменты, ограничения и подтверждения действий. Hermes рассматривается как настраиваемый агент общего назначения с профилями, инструментами, навыками и подключаемыми каналами, включая MCP и мессенджеры. Это учебное сравнение типичных способов организации работы, а не утверждение, что одна система всегда ограничена кодом, а другая всегда автономна. Реальные возможности зависят от версии, конфигурации и прав.

2. Установка и старт из папки проекта

Для Codex CLI откройте официальную инструкцию https://developers.openai.com/codex/cli. Текущий вариант для macOS/Linux: curl -fsSL https://chatgpt.com/codex/install.sh | sh; если уже установлен Node.js и npm, кроссплатформенный вариант: npm install -g @openai/codex. Для Windows выберите Windows-вкладку той же официальной страницы и используйте предлагаемый там способ. Hermes устанавливайте по официальной странице https://hermes-agent.nousresearch.com/docs/getting-started/installation: Windows PowerShell CLI — iex (irm https://hermes-agent.nousresearch.com/install.ps1); macOS/Linux/WSL2 — curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash. Перед запуском установщика прочитайте команду и проверьте домен источника. Если политика учебного или рабочего компьютера запрещает установку, не обходите её: используйте разрешённое личное устройство или демонстрацию преподавателя. Для дополнительной локальной инструкции см. установку Codex и Hermes в Windows и macOS.

  1. Создайте отдельную папку, например cross-tech-practice. В PowerShell выполните New-Item -ItemType Directory -Force "$HOME\cross-tech-practice"; в macOS/Linux — mkdir -p ~/cross-tech-practice. Создайте в ней README.md и небольшой вымышленный документ sample.md для проверки. Это обычные локальные действия студента; права агента на запись на этом этапе не нужны.
  2. Установите Codex CLI и Hermes Agent по актуальным официальным инструкциям для своей ОС. Откройте новое окно терминала, чтобы обновился PATH; проверьте команды codex --version и hermes --version. Запишите версии и точный текст ошибки, если команда не найдена.
  3. Авторизуйте каждый инструмент только предусмотренным официальным способом. Не пересылайте пароль, API-ключ, токен Telegram, содержимое файлов авторизации или секреты в чат, скриншот, AGENTS.md и GitHub.
  4. Перейдите в созданный каталог: в macOS/Linux — cd ~/cross-tech-practice; в PowerShell — Set-Location "$HOME\cross-tech-practice". Проверьте текущий путь через pwd или Get-Location.
  5. Запустите Codex из этого терминала командой codex. В интерфейсе Codex выполните /init. Команда создаёт заготовку AGENTS.md с инструкциями для агента; это не команда Git и не создание удалённого репозитория.
  6. Прочитайте AGENTS.md целиком. Проверьте, что он описывает именно учебную папку, не обещает несуществующих прав и не содержит личных данных или секретов. Исправьте общие или неверные пункты и сохраните файл. Если AGENTS.md уже был, сначала прочитайте его, не перезаписывайте чужие инструкции.
  7. Запустите Hermes из того же терминала командой hermes (после первичной настройки/выбора провайдера по официальному Quickstart: https://hermes-agent.nousresearch.com/docs/getting-started/quickstart) либо укажите текущую папку поддерживаемым вашей версией способом. Дайте read-only запрос: «Прочитай только README.md; назови цель проекта и перечисли, какие факты прямо написаны в файле. Ничего не меняй и не обращайся к внешним сервисам». Сверьте ответ с файлом.

Важно: текущий каталог — это место, откуда агент начинает работу, а не надёжная граница доступа. Профиль или имя модели также сами по себе не ограничивают чтение файлов. Границу определяют фактические системные права, настройки песочницы, доступные инструменты и полномочия MCP-сервера.

3. Матрица доступа: локальные файлы и MCP

MCP (Model Context Protocol) — протокол взаимодействия приложения-агента с MCP-сервером, который может предоставлять инструменты и другие контекстные ресурсы. Сервер бывает локальным или удалённым. Сам протокол не выдаёт права: их определяют приложение, конфигурация сервера, операционная система и подключённая учётная запись. Поэтому проверяйте набор действий, область данных и полномочия сторон.

СредаЧто может быть доступноЧто обязательно выяснитьУчебный предел
Файловая система компьютераЧтение, перечисление, создание и изменение файлов; запуск команд может дать более широкий доступКакой корневой каталог; чтение/запись; есть ли песочница и журнал; что требует подтвержденияТолько учебная папка; никаких личных каталогов и секретов

Это не таблица гарантированных возможностей конкретных Telegram-MCP или Google-Sheets-MCP серверов. Перед демонстрацией преподаватель показывает экран конфигурации и фактический список доступных инструментов. Если состав инструментов неизвестен, действие считается непроверенным и не выполняется.

Матрица примеров контроля, а не линейный рейтинг риска. Оценивайте отдельно: (а) область данных — вставленный текст, отдельный файл, каталог, весь профиль; (б) операцию — читать, писать, выполнять; (в) внешнее воздействие — отсутствует или действует подключённая служба; (г) привилегии — обычный пользователь или администратор. Чтение большого массива может быть чувствительнее записи в одноразовую папку. В практикуме агенту достаточно чтения тестового файла; студент самостоятельно создаёт папку/файлы и выполняет Git-команды. Запись в тестовую папку включается только в отдельном опыте после проверки границы. MCP-действия выполняет преподавательская демонстрация.

4. Демонстрация Hermes в Telegram и проверка доступа

Преподаватель показывает подготовленную учебную группу и два заранее настроенных варианта Hermes: с моделью OpenAI Luna и с моделью StepFun. Затем проводится сопоставимый опыт: (а) текстовый чат без файловых инструментов получает вставленный текст искусственного README; (б) агент Hermes получает доступ только к этому тестовому файлу и тот же вопрос. Запрос в обоих случаях: «Назови цель проекта и три прямо указанных факта. Не додумывай и укажи, откуда взял каждый факт». Запишите вход, ответ и доступный след инструмента. В Telegram преподаватель отправляет отдельный безвредный запрос к тем же искусственным данным и показывает, где видно выбранный профиль/модель. Название модели само по себе не доказывает, что именно она ответила.

  1. Преподаватель отправляет тестовый запрос в демонстрационный бот, например: «Перечисли три темы из учебного README. Не отправляй сообщения другим участникам и не меняй файлы».
  2. Участник проверяет доступ через свой разрешённый маршрут: бот отвечает ли ему в личном чате или в тестовой группе. Достаточен технический результат «ответ получен / не получен» и код ошибки; список имён, телефонов и членства не публикуется. Для сравнения сдайте таблицу «одинаковый вход → переданные данные → ответ → наблюдаемый вызов инструмента/его отсутствие» для чат-бота и агента.
  3. Если бот не отвечает, запишите время, выбранный чат, текст ошибки и что уже проверено. Не присылайте токены и не пытайтесь добавлять себя в чужой список доступа.

Проверка одного участника не доказывает доступ остальных. Членство в группе не доказывает посещение занятия, официальный состав группы или право использовать персональный бот. Настройка доступа участников и список доступа остаются задачей преподавателя; этот материал не меняет групповые настройки и не обещает доступ всем.

О временном --yolo и запуске от администратора. Codex-опция --yolo (синоним опасного режима обхода approvals и sandbox) отключает встроенные подтверждения и песочницу. Как диагностический эксперимент она может показать только, срабатывает ли конкретная операция без этих ограничений; не выясняет, какое разрешение мешало, не исправляет конфигурацию и не подтверждает безопасный штатный запуск. Её нельзя применять на рабочем/личном компьютере с файлами и учётными данными. Если преподаватель проводит сравнение, то только в одноразовой изолированной виртуальной машине без секретов и сети, которую изолирует внешняя среда.

PowerShell «Запуск от имени администратора» повышает системные права самого процесса PowerShell; это не то же самое, что режим песочницы Codex. Запуск установщика с повышенными правами допустим только если официальный установщик этого требует и это разрешено владельцем компьютера. После такой проверки закройте повышенное окно и запускайте агента обычным пользователем. Не обходите отказ корпоративной политики; передайте код и снимок ошибки ИТ-службе.

6. Учебная проверка документов: логика и требования

Внутренняя непротиворечивость — согласованы ли утверждения внутри документа: одинаково ли названы объект, период, метрика и вывод; не расходятся ли цель, задачи, таблицы, заключение и приложения. Соответствие требованиям — выполнены ли пункты внешнего критерия, например разделы, форматы или обязательные элементы. Документ может быть логически согласованным, но нарушать требование; может формально содержать все разделы, но противоречить сам себе. Это два прохода с разными таблицами доказательств.

Для упражнения используйте следующий воспроизводимый вымышленный фрагмент бакалаврской ВКР (не реальную работу): «Тема: связь использования мобильного приложения с расходами студентов. Цель — исследовать связь. Метод — анкета; в разделе “Методы” указано, что получено 150 ответов. В разделе “Результаты” анализируются 150 анкет. В заключении сказано: анализ основан на 120 анкетах. В выводе автор утверждает, что приложение вызвало рост расходов». На сайте Финансового университета опубликовано Положение о ВКР: прямой URL https://www.fa.ru/upload/iblock/d6b/h1eqiv84lut8kek89abfi18so99p7rx5/Prikaz-_-2203_o-ot-18.10.2021.pdf; документ содержит изменения приказами вплоть до 17.12.2025. Для учебного упражнения берём п. 1.3 о бакалаврской ВКР и проверяем только, что представленный фрагмент позволяет подтвердить: самостоятельное законченное исследование, анализ теоретической и/или практической проблемы, демонстрацию готовности к профессиональной деятельности. Фрагмента недостаточно, чтобы подтвердить все эти признаки, поэтому отмечаем их как «не проверено по фрагменту». Для формата и оформления полной работы преподаватель обязан выбрать рекомендации конкретной программы и версию документа. Общая формулировка положения не является полным чек-листом.

Не загружайте собственный или чужой диплом, отзыв, персональные данные, неопубликованные результаты исследования или закрытые рабочие материалы во внешний ИИ-сервис без разрешения автора и проверки правил университета. Для демонстрации достаточно вымышленных абзацев и официального открытого критерия.

Проход A — внутренняя согласованность

  1. Попросите агента составить таблицу «утверждение → место 1 → место 2 → совпадает / расходится / проверить вручную».
  2. Проверьте цель и задачи с выводами; числа и единицы измерения с таблицами; названия объекта, предмета и периода во всех главах; ссылки на таблицы и приложения. Это проверка согласованности документа. Обоснованность вывода (например, вывод о причинности по одной корреляции) отметьте отдельно как методологический вопрос, не как внутреннее противоречие.
  3. В синтетическом примере ожидаемая находка: «150 ответов» в методах/результатах расходится с «120 анкетами» в заключении. Ещё одна находка для проверки основания: наблюдаемая связь не доказывает, что приложение вызвало рост расходов. Запишите цитату/локатор каждого фрагмента и объясните расхождение; не позволяйте агенту молча выбирать верную версию.

Проход B — соответствие требованиям ВКР

  1. Преобразуйте п. 1.3 Положения в список атомарных проверок: (а) самостоятельность и завершённость исследования; (б) анализ одной теоретической и/или практической проблемы; (в) свидетельство подготовленности к самостоятельной профессиональной деятельности. Для данного короткого вымышленного фрагмента ожидаемый результат по каждому широкому признаку — «не проверено по этому фрагменту», а не вывод о нарушении всей ВКР.
  2. Попросите агента искать каждое требование в разрешённом образце. Используйте статусы «выполнено», «не выполнено», «не найдено», «неприменимо», «нужно решение человека».
  3. Требуйте точную страницу/раздел/фрагмент и цитату для статуса. Отсутствие найденного текста означает «не найдено в проверенном материале», а не автоматически нарушение или отсутствие в полном документе.
  4. Человек сверяет все замечания с документом и применимой версией правил, исправляет текст сам и повторяет проверку.

Пример промпта: «Проверь только приложенный обезличенный учебный фрагмент. Сначала перечисли проверенные файлы и критерии. Отдельно найди внутренние расхождения и отдельно проверь соответствие каждому пункту критерия. Для каждого замечания приведи обе цитаты или страницу критерия и точное место в тексте. Разделяй факт, гипотезу и вопрос автору. Не исправляй файл; неизвестное отмечай как “не проверено”.»

Проверяемый результат: две таблицы замечаний, каждая с источником и локатором; список непроверенных критериев; краткое решение человека «подтверждено / отклонено / нужно уточнение». Агент не ставит оценку ВКР, не подтверждает академическую добросовестность и не заменяет руководителя, нормоконтроль или комиссию.

7. Рефлексия, OODA и развитие навыка

OODA — цикл Observe, Orient, Decide, Act: наблюдать, осмыслить обстановку, решить и действовать. В практикуме это не лозунг «действовать быстрее», а способ отделить сигнал от предположения, выбрать безопасный следующий шаг и проверить фактическое изменение. Рефлексия и улучшение инструкции — внешний учебный контур над OODA, а не дополнительная фаза исходной модели. Человеческий навык формулирования запросов развивается повторением; редактирование файла SKILL.md меняет инструкцию, но не веса модели и не является автономным самообучением агента. После выполнения раздела 8 цикл проводят на отдельной копии навыка или проектной инструкции, не редактируя установленный общий навык вслепую.

  1. Observe — наблюдать. Зафиксировать версию инструмента, путь, режим разрешений, точную ошибку, доступный журнал и фактическое состояние файла.
  2. Orient — осмыслить. Отнести проблему к слою: установка, сеть, авторизация, путь, доступ к файлам, MCP, качество документа или неверный критерий. Развести факт и объяснение.
  3. Decide — решить. Выбрать минимальную проверку с малым риском: прочитать один синтетический файл, уточнить одну настройку, проверить один пункт требования.
  4. Act — выполнить. Запросить действие в установленной границе, получить подтверждение при необходимости, проверить файл/ответ сервиса и записать результат.
  5. Рефлексия → улучшение навыка. Сравнить ожидаемое и наблюдаемое, отметить ошибку инструкции, внести одно ясное изменение в личный или проектный skill, повторить тот же тест на том же искусственном примере. Сохранять версии и причину изменения; откатывать улучшение, если повторяемость ухудшилась.

Так получается цикл улучшения человеческого навыка и проектной инструкции: задача → гипотеза → тест → наблюдение → разбор ошибки → небольшое изменение → повторный тест. «Самообучение» здесь — только условная метафора для управляемой человеком рефлексии; агент не меняет самовольно свои правила, системные права или модель.

8. Два навыка и краткий отзыв

Установите два навыка для Codex и после установки перезапустите Codex, чтобы он перечитал список навыков. Источники: https://github.com/strato-space/greek-scholastic и https://github.com/iqdoctor/logika.

  1. greek-scholastic: вызовите встроенный $skill-installer и укажите источник https://github.com/strato-space/greek-scholastic/tree/main/greek-scholastic. Репозиторий также документирует альтернативную команду Skills CLI: npx skills add strato-space/greek-scholastic --skill greek-scholastic.
  2. https://github.com/iqdoctor/logika: следуйте разделу Install в README; для Codex репозиторий указывает каталог ~/.codex/skills/logika/, куда копируется или клонируется папка навыка так, чтобы SKILL.md находился в корне этой папки. Проверьте имя каталога logika и перезапустите Codex.

Перед установкой просмотрите содержимое и лицензию источника. greek-scholastic помогает проверить, какие сущности и понятия описаны и не смешаны ли разные категории; logika помогает проверить выводы и ошибки аргументации. Навык задаёт инструкции для агента, но не выдаёт ему новых системных прав.

Примените greek-scholastic к главному описательному файлу своего тестового проекта (обычно README.md). Если его нет, создайте короткое учебное описание сами. Попросите не переписывать файл, а дать не более трёх замечаний: что утверждается, какие понятия/объекты смешаны или не определены, что можно минимально уточнить. Для каждого замечания попросите указать строку/фрагмент и основание. Затем отдельно пропустите один вывод через logika; проверьте, следует ли заключение из приведённых посылок.

Краткий отзыв должен отделять наблюдение от оценки: «В тексте X сказано…; это не согласовано с Y / термин Z не определён; предлагаю уточнить…». Примите только замечания, подтверждённые самим файлом или критерием. Сам факт запуска навыка не подтверждает правильность его ответа.

9. GitHub: история и дополнительная копия

Git хранит локальные версии изменений. GitHub хранит удалённый репозиторий и позволяет иметь ещё одну копию проекта и историю коммитов. Создание учётной записи и private-репозитория — отдельные действия; слово private ограничивает видимость, но не создаёт копию автоматически. Для резервной копии нужен зафиксированный коммит, отправленный в удалённый репозиторий, и проверка, что нужные файлы там присутствуют.

  1. Если у вас нет аккаунта GitHub, зарегистрируйтесь на https://github.com/signup, используя собственную почту и уникальный пароль. Не передавайте пароль преподавателю или агенту.
  2. Создайте новый репозиторий как Private. Не загружайте в него чужой проект, персональные документы, диплом, токены, учётные данные, файл авторизации или материалы курса, на публикацию которых у вас нет разрешения.
  3. Создайте локальную историю: в папке проекта выполните git init, проверьте git status, добавьте только учебные файлы командой git add README.md sample.md, создайте коммит git commit -m "Начало учебного проекта". Затем следуйте руководствам GitHub: создание пустого репозитория — https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository; отправка локального кода — https://docs.github.com/en/repositories/creating-and-managing-repositories/adding-locally-hosted-code-to-github. Используйте URL именно созданного репозитория, затем выполните показанные GitHub команды привязки remote и git push -u origin main. Перед отправкой ещё раз проверьте состав файлов и исключите секреты.
  4. Проверьте на странице GitHub имя private-репозитория, последний коммит и наличие учебного README. Для проверки восстановления можно клонировать репозиторий в новую пустую папку и открыть копию. Не считайте незапушенные локальные изменения резервной копией.

10. Скриншот и сдаваемый результат

Скриншот должен показывать ошибку или нужную настройку и контекст, достаточный для разбора: приложение и версия, введённая команда (если она безопасна), текущий каталог и полный текст ошибки. Перед отправкой закройте или замажьте имя пользователя, почту, имена чатов, личные документы, токены, QR-коды, API-ключи, экран авторизации и пути к секретам. Никогда не прикладывайте auth.json, конфигурацию с секретами или переписку с личными данными.

К сдаче приложите: версии Codex/Hermes; путь к учебному каталогу; краткую проверку AGENTS.md; одну запись о фактическом действии агента; матрицу доступа по примеру; две таблицы проверки документа; три коротких итога по OODA/рефлексии; отзыв по навыку; ссылку или снимок private-репозитория без личных данных. Если шаг недоступен, укажите «не проверено» и приложите безопасно очищенный текст ошибки.
