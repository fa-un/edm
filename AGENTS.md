# Правила ведения учебного репозитория

Эти инструкции относятся к созданию и обновлению материалов курса «Управление данными предприятия» и его HTML-страниц в этом репозитории.

Для сверки и группировки пользователей 1С используй служебную инструкцию [«Работа агента с пользователями 1С»](Аттестация/Служебная-инструкция-по-пользователям-1С.md). Она фиксирует проверенные маршруты интерфейса и ограничения текущего личного кабинета.

## Отдельная дисциплина: «Сквозные технологии цифровой экономики»

- Это самостоятельный предмет со своим составом обучающихся. Не включай его страницы, литературу, транскрипты и исходные материалы в тематический индекс или каталог ресурсов дисциплины «Управление данными предприятия». Для каждого предмета сохраняй отдельную страницу дисциплины и внутреннюю навигацию.
- Список участников чата Telemost подтверждает только членство в чате, а не посещение занятия или официальный состав группы. Списки ФИО и оценок храни в закрытых/локальных материалах; не публикуй их на GitHub Pages по умолчанию.
- Материалы конкретных ВКР, исследований и индивидуальных кейсов веди в соответствующих отдельных репозиториях. Не переноси их исходники, переписку, транскрипты и индивидуальные результаты в репозиторий или индекс курса; используй в курсе только отдельно согласованные и обезличенные учебные обобщения.

## 1. Организация курса и индекса

- Главная страница сайта — [`index.html`](index.html). Это тематическая программа и навигация по материалам, а не список встреч.
- Показывай темы отдельными разделами страницы, а ссылки на лекции, практикумы, методические пособия и записки размещай внутри соответствующей темы. Не собирай материалы разных тем в параллельные таблицы.
- Текущий порядок разделов индекса:
  1. **Роль Аналитика ERP/MES/CRM системы**
  2. **Производство в ERP**
  3. **Управление активами (ТОиР)**
  4. **Логистика**
  5. **Управление финансами**
  6. **Управление данными**
  7. **Управление проектами и модули системы**
  8. **Онтология и карта знаний**
- Онтология и карта знаний — новая тема тематического индекса. Пока в ней опубликованы интерактивная карта и извлечённые понятия; соответствие РПД и проведение занятий не подтверждены, карта не является схемой фактической конфигурации 1С. Содержание лекций и практикумов не перерабатывай без предварительного предложения на согласование; исправляй в них только обратные ссылки, ставшие неверными из-за перемещения материала.
- Логистика находится после управления активами, поскольку занятия по ней ещё не было. Этот порядок показывает последовательность курса в индексе; не выдавай его за официальную нумерацию РПД, если она отличается.
- Для темы 1 указывай методическое пособие **«Концепция прикладного решения ERP»**. Для тем производства и управления активами — **«Управление производством и ремонтами в ERP»**. Методические пособия доступны студентам в личном кабинете. Не представляй их как файлы репозитория, если локального файла нет.
- В теме 2 располагай лекцию и практикумы № 1–8. Если авторские разборы есть только для части практикумов, указывай ссылки на существующие разборы, а для остальных — источник методического задания и отсутствие отдельного авторского разбора.
- В теме 3 размещай материалы по ТОиР, включая пояснительную записку и соответствующее методическое пособие.
- В индексе и хронологии ссылайся на канонические страницы актуальных материалов. Страницы-перенаправления оставляй только для совместимости старых ссылок; не считай их отдельными материалами и не перечисляй как самостоятельные разборы.
- Для темы, по которой ещё нет занятий или авторских материалов, оставляй короткое пояснение вместо пустого списка или выдуманного содержания.
- Разделяй студенческий материал и сценарий преподавателя: поминутный план и преподавательские подсказки размещай в сценарии, а в навигации явно помечай его аудиторию. Связывай соответствующие страницы между собой.
- Официальную ссылку с названием **«Рабочая программа дисциплины»** веди на <https://fa-un.github.io/edm/>.
- Главная тематическая программа курса — [`index.html`](index.html). [`INDEX.md`](INDEX.md) остаётся короткой ссылкой на неё, а не отдельным индексом.

## 2. Даты и сведения о занятиях

- Рядом с материалом указывай только дату создания первой версии самого материала в формате `ДД.ММ.ГГГГ`, без пояснительного текста.
- Для производных форматов (например, HTML-версии md-файла) не добавляй отдельную дату.
- Для загруженных материалов сначала используй дату создания, встроенную в файл; дату из имени файла используй, если она однозначна. Не подменяй исходную дату датой скачивания, последнего изменения, коммита или публикации.
- Не выводи дату проведения занятия из даты файла. Даты встреч включай только при наличии прямого подтверждения; если точная дата неизвестна, её можно не указывать.
- Не придумывай факт проведения, посещения или завершения практикума. Отделяй подтверждённое от запланированного.
- Для пособий и иных внешних файлов без подтверждённой даты не добавляй предполагаемую дату.

## 3. Материалы и версии

- Основной формат авторских учебных материалов — HTML. Весь материал должен быть доступен на GitHub Pages и оставаться удобным на экране и при печати.
- Если рядом с HTML сохраняется файл `.md`, он служит короткой ссылкой на соответствующую опубликованную HTML-страницу, а не второй полной версией материала. Исключения — служебные инструкции репозитория и исходные данные, которые нужны для анализа.
- Имена парных файлов должны совпадать, меняется только расширение. Сохраняй принятый стиль имён репозитория и номера практикумов.
- В HTML-странице добавляй ссылку на главную программу курса и на связанные HTML-материалы. Не добавляй ссылку на Markdown-заглушку как на альтернативную версию.
- HTML должен оставаться самостоятельным статическим документом, пригодным для просмотра на компьютере, телефоне и печати. Подключай общую таблицу стилей `assets/styles.css`; оставляй в HTML смысловую структуру и содержимое. Исходные файлы и медиа храни в `assets/`, перечисляй их в `assets/index.html`, а картинки — в `assets/images/index.html`. Не делай доступ к основному содержанию зависимым от внешнего сервиса.
- Если в Pages публикуются исходные файлы PDF, PPTX или другие вложения, добавляй сами файлы в репозиторий, прямую ссылку на скачивание — в соответствующую тему индекса, а расширение файла — в список копируемых форматов workflow `pages.yml`.
- Включай в страницы только материалы, реально присутствующие в репозитории или доступные по явно приведённой ссылке. Для материалов из личного кабинета указывай, где их найти, но не создавай несуществующие ссылки.
- Если студенту нужно открыть или скопировать внешний ресурс, показывай полный прямой URL `https://…` в соответствующем разделе страницы, а не только ссылку с названием.
- Сохраняй ссылку на источник и привязывай утверждения к доступному учебному материалу (РПД, методическому пособию, презентации или заданию). Если источник недоступен, не приписывай ему не проверенные значения.

## 4. Определения и схемы создаваемых объектов

Открывай материал коротким объяснением задачи предприятия: зачем нужна область или подсистема и какой результат получит студент. Для практикума затем давай общую обзорную карту создаваемых объектов, для лекции — короткую схему рассматриваемого процесса или связи понятий. После обзора объясняй общие понятия курса; специальные термины вводи в нужном разделе перед подробной схемой или объяснением. Одно понятие определяй в документе один раз: в следующих разделах используй термин или ссылку на определение. Общие и специальные определения не дублируй. Сначала объясняй базовые понятия предметной области, затем вводи сокращения и термины 1С/ERP. Определение должно быть понятным без предварительного знания системы: назови класс вещи/данных/действий, укажи отличительный признак и роль в работе предприятия, затем дай короткий пример из занятия. Рабочая форма: «X — это [что за объект, правило или действие], которое [чем отличается]. В работе оно нужно, чтобы [роль]. Например, [пример из занятия]». Не определяй термин через тот же термин, цепочку незнакомых слов или сухую формулировку из интерфейса; если важны связь или назначение, объясни их простыми словами. Если парное или составное понятие опирается на самостоятельные термины (например, «план-факт»), сначала отдельно определи каждое из них, затем объясни связь.

В заголовках и пояснениях используй обычные предметные слова. Не вводи академический метатермин, если ту же мысль можно выразить простым названием связи или объекта; специальный термин оставляй, когда он нужен студенту, и сразу объясняй.

### Разбор возможных проблем и отклонений

После краткой схемы процесса покажи ожидаемый результат предприятия. Если тема разбирает возможные проблемы, сгруппируй их по этапам процесса или по проверяемым условиям, таким как срок, количество или качество. Выделяй ситуацию отдельно, если для неё нужны свои данные, ответственный или действие. Используй принятый деловой термин и поясняй его простыми словами. Названия документов, полей и операций 1С:ERP сверяй с источником. Указывай схему учёта, если от неё зависит способ регистрации.

Для каждой ситуации покажи, **что проверяют**, **что делают заранее** и **как действуют при отклонении**. Укажи, с чем сравнивают факт и откуда берут данные. Например, срок берут из заказа, а дату фактического поступления — из записи о приёмке. Назови ответственного, если его роль помогает понять, кто проверяет данные или принимает решение. Связывай каждую меру с конкретным отклонением.

Различай возможный риск, выявленное отклонение и его причину. Если по данным виден только признак, укажи, что проверить дальше. Например, заказано 60 кг, в накладной 50 кг и принято 50 кг. Это недопоставка по заказу, а количество в накладной совпадает с фактом. Показывай назначение документов 1С и отдельно описывай действия предприятия.

Методическая опора — [FPF C.22.2:3](https://fpf.tools/C.22.2:3) для различения признака, возможной и установленной проблемы, [FPF A.15:12d](https://fpf.tools/A.15:12d) для различения плана, события и записи о нём и [OPS.18:4.1](https://fpf.tools/OPS.18:4.1) для связи ожидаемого результата, требования и действия. В учебном тексте передавай эти различия простыми словами.

### Пошаговые материалы и схемы

Для пошаговых учебных материалов каждый экран или действие связывай с задачей: перед скриншотом укажи, что студент делает; после него простыми словами объясни, что изменилось в данных и зачем. Отделяй маршрут по интерфейсу от карты объектов: карта показывает, что создаётся и как связано, а инструкция — где выполнить действие. Добавляй короткий блок частых вопросов только для реальных затруднений; на каждый вопрос дай прямой ответ и ссылку на раздел или слайд, где это разобрано.

Для практической работы извлекай из задания и экранных форм конкретное содержание упражнения: какие записи создаются, какие поля задаются, какие строки таблиц добавляются и как записи используются на следующем шаге. Не пересказывай интерфейс вместо объяснения объектов и их назначения.

Если упражнение создаёт объекты, показывай две согласованные схемы в таком порядке:

1. **Краткая схема и общая карта** — обзорное текстовое дерево создаваемых объектов. Оставляй типы объектов, понятные группы и главные этапы; не показывай пиктограммы, поля, значения атрибутов, строки таблиц и технические ссылки между реквизитами. Простую стрелку оставляй только для понятного перехода создания документа, например «заказ на ремонт → заказ на производство». Количество указывай только для двух или более объектов; одиночный экземпляр не помечай как «отдельная запись», «1 запись», «1 объект» или «1 шт.».
2. **Подробная схема** — показывает точные связи объектов и структуру их карточек. Дополняй её типами записей, учебными наименованиями и только теми атрибутами, которые задание требует задать или изменить относительно начальных значений. Не перечисляй неизменяемые значения по умолчанию. Поля и значения записывай явно в формате `Ключ: значение` и связывай с источником.

Если практическая работа состоит из связанных разделов, перед подробными схемами добавляй одну общую обзорную карту всего практикума: покажи в одном текстовом дереве создаваемые объекты, их главные группы и простые переходы между разделами. Детальные ссылки и подчинение оставляй подробным схемам.

Не добавляй абзацы о том, как устроен сам документ, почему выбрана его структура или какие правила оформления применены. Не пересказывай соседнюю схему абзацем или повторной таблицей. Текст рядом оставляй, когда он объясняет причину, различие понятий, исключение или способ проверки, которых не видно на схеме. Оставляй только объяснение, которое помогает понять область предприятия, цель создания объекта, его назначение, связи с другими объектами и ожидаемый результат.

При необходимости поясняй обозначения схемы: реквизит-ссылка хранит выбор другого объекта; таблица содержит строки со ссылками, количествами и другими данными. Подписывай отношения явно: отступ сам по себе не означает физического подчинения, а обозначает только связь, указанную в подписи (например, состав, принадлежность или переход по ссылке). Стрелка «на основании» обозначает создание документа.

В подробной схеме обозначай тип связи словом или пиктограммой: «реквизит-ссылка →», «строка таблицы →», «принадлежит», «входит в физический состав», «создаётся на основании». Вложенность отступом сама по себе не означает физического подчинения.

Чтобы подробная схема не разрасталась текстовыми метками, используй единый набор пиктограмм: `↗` — реквизит-ссылка; `□` — реквизит; `▦` — таблица; `▬` — строка таблицы; `▣` — раздел карточки. Перед первой подробной схемой дай короткую видимую легенду. В обзорных деревьях пиктограммы не используй. Не заменяй пиктограммами имена полей, значения или направление связи. В HTML сохрани текстовое название каждого символа в легенде и доступное имя (`aria-label` или `title`) у пиктограмм подробных схем.

Каждый создаваемый именованный объект обозначай жирным заголовком с типом и главным атрибутом, например:

> **Объект эксплуатации: Наименование: Технологическая установка xx.yy**

Для других именованных объектов используй тот же шаблон: `Тип объекта: Наименование: значение`. Для документа вместо «Наименование» показывай его главный идентификатор или ссылку на ключевой объект, например `Заказ на ремонт: Объект эксплуатации: Технологическая установка xx.yy`; номер используй, если он задан или доступен.

Для длинного перечня однотипных записей сохраняй компактность таблицей вместо повторяющихся карточек: укажи тип объекта и главный атрибут в заголовке колонки, выдели каждое имя жирным и вынеси задаваемые атрибуты в соседние колонки. Не прячь тип объекта или смысл имени в контекстном абзаце.

Под заголовком перечисляй только реквизиты, которые упражнение задаёт или изменяет относительно значений по умолчанию, построчно в формате `Ключ: значение`. Состав таблицы показывай отдельно, перечисляя значения каждой существенной строки в том же формате. Не заполняй карточки неизменяемыми стандартными значениями и не заменяй реально заданные поля общим текстом вроде «настроить параметры».

Используй значения из задания, учебного варианта или слайда. Если конкретное значение зависит от студента или не задано источником, прямо пиши «по варианту студента», «заполняется по шаблону» или «значение в источнике не указано». Не придумывай значения и не превращай условный текст в якобы точное имя поля.

Различай и явно обозначай:

- отдельную запись справочника;
- реквизиты этой записи и ссылки на другие записи;
- таблицу и её строки;
- строку/этап/операцию внутри норматива;
- документ, созданный для конкретного события, и его связь «создать на основании»;
- нормативное описание, план конкретных работ и факт выполнения. Создание заказа или изменение его статуса само по себе не подтверждает выполненную работу; факт требует регистрации результата и использованных ресурсов.

После каждой схемы указывай проверяемый результат: какие записи созданы, какие ссылки и табличные строки заполнены и какой статус требуется заданием.

Перед публикацией проверь каждую ветвь схемы по источнику: тип и количество записей, кто содержит таблицу или строку, куда ведёт ссылка и на основании какого документа создаётся следующий. Однотипные отдельные записи показывай раздельными ветвями; общую номенклатуру, связывающую нормативы, обозначай явно. Не изображай ссылку или общий результат как физическое подчинение. Не объединяй несколько документов в одну карточку. Сверь количества объектов и строк в краткой карте, подробных карточках и итоговой сводке. Не оставляй итоговое число, которое не подтверждается перечисленными ветвями или записями. Сверяй каждую краткую схему с заголовком её раздела и подробной схемой: упрощение не должно терять создаваемые типы объектов или переносить дерево в соседний раздел. При массовых правках привязывай схемы к идентификатору или заголовку раздела, а не к порядковому номеру совпадения.

## 5. Публикация сайта

- Сайт — статические HTML-страницы и Markdown-ссылки из этого репозитория. Публикацию выполняет workflow [`.github/workflows/pages.yml`](.github/workflows/pages.yml) после обновления ветки `main`; служебный `AGENTS.md` в сайт не копируется.

После проверки перенеси завершённую задачу в `main` обычным fast-forward push или через настроенный процесс слияния; push только feature-ветки не запускает публикацию Pages. ## Landing the Plane (Session Completion)

**When ending a work session**, you MUST complete ALL steps below. Work is NOT complete until `git push` succeeds.

**MANDATORY WORKFLOW:**

1. **File issues for remaining work** - Create issues for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **PUSH TO REMOTE** - This is MANDATORY:
   - Fetch and inspect `origin/main`; make sure the reviewed commit is based on the current upstream.
   - If local and remote histories diverged or have no common ancestor, do not run an automatic `git pull --rebase`. Keep the old branch as a backup, start from a fresh `origin/main`, and transfer only reviewed changes.
   - Land the reviewed commit on `main` using the repository's normal merge route, then push without force. A feature-branch push alone does not publish GitHub Pages.
   - Verify the Pages workflow and the published page; check `git status` afterward.
5. **Clean up** - Clear stashes, prune remote branches
6. **Verify** - All changes committed AND pushed
7. **Hand off** - Provide context for next session

**CRITICAL RULES:**
- Work is NOT complete until `git push` succeeds
- NEVER stop before pushing - that leaves work stranded locally
- NEVER say "ready to push when you are" - YOU must push
- If push fails, resolve and retry until it succeeds
