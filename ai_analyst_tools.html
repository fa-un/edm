AI-инструменты аналитика

Разберём, как аналитик использует агента, автоматизацию и проверку рассуждений: от свидетельства и интервью — к проверяемому требованию и плану.

Задача аналитика

В первой лекции аналитик исследует работу предприятия и переводит потребность в проверяемое требование. AI помогает быстрее разобрать материал и подготовить черновик, но вывод нужно сверить с источником.

процесс → проблема → потребность → свидетельство → факт / гипотеза / неизвестное → проверяемое требование → проверка результата

Что вы сможете после занятия

  • Сверять саммари с исходным учебным диалогом и указывать реплику, подтверждающую вывод.
  • Различать факт, гипотезу и неизвестное, формулировать вопросы для уточнения.
  • Составлять черновик требования с условиями и наблюдаемым результатом проверки.
  • Проверять предложенные AI выводы и изменения файла; при доступном Git — просматривать подготовленный diff.

Эти умения развивают работу с процессами, данными и требованиями из первой лекции на примере кейса семинара о закупке.

В IT4IT выделяют четыре потока ценности: Strategy to Portfolio, Requirement to Deploy, Request to Fulfill, Detect to Correct. Для занятия используем простую учебную рамку Plan — Build — Deliver — Run; это не официальные эквиваленты потоков IT4IT. Здесь тренируем аналитический вход в цикл: понять ситуацию и сформулировать, что должно измениться.

Почему одной записи саммари недостаточно

Запись сохраняет первичный источник, к которому можно вернуться и проверить контекст. Расшифровка превращает речь в текст, который проще искать и цитировать. Саммари сжимает материал до основных тем и может опустить условия, оговорки или неизвестные детали. Сверяйте важный вывод с расшифровкой, а при спорном месте — с записью.

mymeet.ai — пример сервиса для записи/обработки встреч, расшифровки и резюме. Его показ преподавателем необязателен: ниже готовая учебная симуляция, и она не создана mymeet.ai. Письменное упражнение показывает, что может потеряться при сжатии; оно не проверяет качество распознавания речи.

Практика: найдите нюанс, потерянный в саммари

Ролевая симуляция — учебный фрагмент на основе кейса семинара о заявке на закупку, не цитата реального интервью. Формулировки диалога придуманы для упражнения. Сравните текст с кратким саммари и сами найдите, какое существенное условие выпало.

Имитация расшифровки

Аналитик: Какой результат хотим получить?

Участник процесса: Чтобы заявка быстрее доходила до закупок. Сейчас в среднем уходит десять рабочих дней, хотелось бы уложиться в три.

Аналитик: Можно убрать финансовое согласование?

Участник процесса: Нет, финансовый контроль должен сохраниться. Когда данных не хватает, заявку возвращают мне, а её текущий статус я не всегда понимаю.

Аналитик: Сколько времени занимает каждый этап?

Участник процесса: Не знаю. Это нужно отдельно посмотреть.

Краткое саммари

Нужно сократить срок передачи заявки в закупки с 10 до 3 рабочих дней. При неполных данных заявку возвращают, статус не всегда понятен. Длительность этапов требует дополнительного анализа.

Задание: сравните тексты. Какое обязательное ограничение есть в диалоге, но исчезло из саммари? Укажите источник; отделите подтверждённый факт от неизвестного; не придумывайте причину задержки.

Результат в analysis.md

## Проверка саммари
- Потерянный нюанс: [укажите условие и точную реплику-основание]
- Факт: [что прямо подтверждено материалом]
- Гипотеза: [возможное объяснение, которое ещё нужно проверить]
- Неизвестно: [каких данных или правил не хватает]
- Черновик требования: система должна [действие/условие]
  для [сценария/пользователя].
- Проверка: задайте входные условия и ожидаемый результат;
  включите обычный и исключительный сценарий.
- Вопрос аналитику: [что нужно уточнить у участника процесса?]

Например, из известной проблемы неясного статуса можно сформулировать проверку: при возврате неполной заявки пользователю видны её статус и причина возврата. Укажите сценарий, действие системы и наблюдаемый результат; ограничения решения уточняйте по источнику.

Это черновик: роль проверяющего, правила и сценарии приёмки нужно уточнить. Десять дней — значение, сообщённое участником, а не проверенное измерение; три дня — желаемый результат, а не уже достигнутый факт. Если Git и учебный репозиторий доступны, выполните git add analysis.md, затем git diff --cached -- analysis.md. Просмотрите, что именно попадёт в следующий коммит; пока не отправляйте материал в общий репозиторий.

Личная среда: подготовить до занятия

  1. Установить Git и проверить в терминале: git --version.
  2. Для подготовки следующего уровня войдите в личную учётную запись GitHub; для основной локальной практики она не требуется.
  3. Установить Codex Desktop, войти в собственную учётную запись Codex/ChatGPT и проверить, что приложение запускается.
  4. Открыть в Codex Desktop подготовленную учебную папку. Вход в GitHub и установка GitHub CLI (gh) для основной практики не нужны.

Проверьте перед началом: команда git --version выводит версию, Codex Desktop запускается под вашей учётной записью, учебная папка открывается и содержит диалог и саммари. Для команд Git папка должна быть подготовленным репозиторием.

Если Codex или Git недоступен: прочитайте диалог и саммари на этой странице, заполните все пункты шаблона в любом текстовом редакторе или на бумаге и сверьте ответ с таблицей критериев. Используйте демонстрацию преподавателя, если она доступна, Если Git недоступен, отдельно отметьте, что проверку изменений через него выполнить не удалось; если недоступен Codex, отметьте, что самостоятельно проверить работу агента не удалось. Анализ и требование можно выполнить без установки.

Преподаватель может показать функции на отдельной учётной записи Codex с небольшим лимитом; студенты в неё не входят и её данные не получают.

Чат-бот обычно отвечает текстом в окне. Кодинг-агент вроде Codex может работать с файлами выбранного проекта и выполнять разрешённые команды; поэтому проверяйте его действия и изменения по файлам и diff. В Desktop это показано в приложении, CLI делает похожую работу из терминала.

Запрос для Codex: «Сравни учебный диалог и саммари в этой папке. Укажи конкретную пропущенную оговорку с цитатой, раздели факты, гипотезы и неизвестное. Предложи черновик проверяемого требования и вопросы для уточнения. Не дополняй сведения догадками; запиши результат в analysis.md».

Сценарий 1: отчёт 1С и ведомость

Преподавателю нужно узнать, какие действия студент выполнял в учебной базе, и сопоставить их с заданием. Ниже — учебная ситуация по мотивам реальной работы с отчётом. Даты, числа и отметка вымышлены; они не относятся к конкретному студенту.

В отчёте «Активность пользователя» за 01.03–15.03 видны 5 введённых и 3 изменённые записи 10.03. При другом запросе на три недели, 23.02–15.03, агент открыл детальный отчёт, но после формирования начальная дата вернулась к 01.01. Отчёт за 01.01–15.03 показал 20 введённых и 8 изменённых записей. Этот итог не является итогом за запрошенные три недели.

Как устроена автоматизация интерфейса

RPA — автоматизация повторяемых действий в интерфейсе программы: она нужна, когда данные получают через привычные человеку формы. В этом примере агент управлял браузером: читал доступное состояние страницы и элементы формы, выбирал отчёт и пользователя, вводил даты, нажимал кнопку формирования и снова считывал результат. Цепочка: задача → состояние экрана → действие → новое состояние → проверка результата. Это была работа агента с интерфейсом, а не доказательство того, что использовался заранее записанный робот или прямой доступ к базе.

Детальный отчёт «Активность пользователя» и сводный «Анализ активности пользователей» — разные отчёты; во втором может быть выбран не один человек. Интерфейс может сбросить фильтр или показать другой отчёт. Перед выводом проверьте название отчёта, пользователя и обе даты после формирования; при несоответствии не переносите итог в ответ как результат нужного периода. Названия и расположение полей зависят от конкретной базы.

Как связать отчёт с таблицей через MCP

MCP (Model Context Protocol) — способ подключать агенту внешние инструменты через описанные интерфейсы. При работе с Google Sheets клиент агента вызывает доступный инструмент подключённого сервиса; тот обращается к таблице с предоставленными правами и возвращает данные. Типовая цепочка: запрос → чтение листа и нужной строки → сопоставление с источником → разрешённая запись ячейки → повторное чтение. Доступ к таблице и набор доступных действий зависят от подключения. MCP не определяет смысл оценки и не подтверждает правильность исходных данных.

В учебном примере преподаватель распорядился внести демонстрационные 2 балла в ведомость. Событие в 1С, выполненное задание и оценка — разные вещи: даже правильная запись ячейки не доказывает, что работа выполнена к нужной дате. Демонстрационную отметку нужно явно обозначать; для реальной оценки нужны объекты и критерии задания.

Задание: укажите, какие даты нужно проверить после формирования отчёта; можно ли использовать итог за январь–март как трёхнедельную статистику; какое свидетельство нужно до записи реальной оценки. Ответ обоснуйте приведёнными данными.

Сценарий 2: проверка вывода об активности

Онтологическая проверка выясняет, о каких разных объектах или событиях говорится и какую роль они играют в выводе. Логическая проверка рассматривает посылки и переход к заключению: следует ли вывод из имеющихся оснований. Обе проверки помогают найти ошибку, но не заменяют проверку фактов в источнике.

Рассмотрим утверждение: «В отчёте есть изменения объектов 10 марта; значит, студент выполнил практикум к 5 марта». Операция в системе — событие; результат практикума — созданные студентом объекты или выполненная работа; проверка соответствия сопоставляет результат с заданием и критериями; отметка фиксирует оценку. Это разные вещи. Посылки не связывают изменения с нужным заданием и не подтверждают выполнение к более ранней дате. Осторожный вывод: отчёт показывает активность 10 марта; связь с практикумом и сроком требуется проверить.

Навык greek-scholastic предлагает сначала уточнить понятия и типы обсуждаемых вещей, затем проверить основания и степень уверенности. Logika помогает выделить посылки, скрытые допущения и проверить форму вывода. Даже корректная форма рассуждения не делает исходные посылки истинными. Результат каждого навыка проверяет аналитик.

Задание: запишите посылку и вывод из примера, назовите недостающее основание и предложите проверяемую формулировку. Сравните свой ответ с разбором выше.

Сценарий 3: от интервью к плану приложения экипажа

Заказчик описал приложение для бортпроводников: личное расписание и стыковки, сведения о назначенной гостинице, работу без связи и отправку инцидента после её восстановления. Это пересказ интервью о проекте; приложение на момент планирования ещё не было создано.

Как уточнять неизвестное

Сократическое интервью — последовательность вопросов, где каждый ответ помогает уточнить смысл задачи и выбрать следующий вопрос. Например: «У кого расписание?» → у каждого бортпроводника своё; «Кто меняет назначения?» → наземная система; «Кто регистрирует инцидент?» → старший бортпроводник. Подтверждение означает принятие назначения к исполнению; срочное изменение должно прийти push-уведомлением, после чего пользователь подтверждает его в приложении. Инцидент содержит тип, описание, рейс и время; сведения о гостинице поступают из системы размещения. Из ответов получаются роли и границы полномочий, а не готовый код.

Для неподтверждённого назначения заказчик назвал напоминания через 5, 15 и 40 минут и затем звонок оператора. Не установлено, считаются ли интервалы от назначения или последовательно друг после друга. Это открытый вопрос: нельзя незаметно выбрать вариант и объявить его подтверждённым требованием.

Как проверять план

oh-my-codex — набор рабочих процессов для Codex. В использованном процессе интервью идёт раундами: выявить неизвестное → задать вопрос → записать ответ → пересмотреть оставшиеся вопросы. Оценка остаточной неопределённости помогает решить, что уточнить, но не является измеренной вероятностью правильности.

Затем планировщик составляет план, архитектор и критик отдельно проверяют его, замечания возвращаются на доработку, и проверка повторяется. В рассматриваемом проекте отдельно проверяли различие между подтверждением на телефоне без сети и принятием сервером, а также риск подтверждения старой версии назначения после появления новой. Для демонстрационного прототипа план предусматривал только вымышленные данные; для настоящих расписаний и инцидентов нужен отдельный защищённый контур. Независимые роли помогают обнаруживать пропуски, но согласие агентов не гарантирует правильность плана: человек сверяет замечания с интервью и решает, что осталось неизвестным.

Задание: составьте два вопроса заказчику: один об офлайн-подтверждении, другой — об отсчёте напоминаний. Для одного вопроса покажите, как разные ответы изменят требование; затем предложите проверку: на телефоне принято назначение версии N без сети, до синхронизации появилась версия N+1. Какое состояние нужно показать и какую версию сервер вправе считать подтверждённой?

Рабочая ориентация на занятии, не универсальная гарантия возможностей: Luna — быстрые экономные задачи, Sol/Terra — повседневная работа, Astra — сложные задачи, где качество может оправдать больший расход; делегируйте агентам независимую работу с ясным результатом и проверкой.

Данные и следующий уровень

Для заданий используйте только учебные примеры на этой странице. Реальную запись можно обрабатывать только при согласии участников и разрешении владельца данных с учётом правил организации. Не загружайте в облачные сервисы рабочие документы, персональные данные, пароли и ключи без согласованного основания. Локальная программа не обязательно использует локальную модель: до передачи данных выясните, где выполняется обработка. Локальная модель тоже не гарантирует безопасность сама по себе.

Как применить дальше: при изучении процесса в 1С сначала проверяйте наблюдения и правила у участников, затем описывайте нужное изменение. При построении схемы процесса или формулировке пользовательской истории отделяйте подтверждённые шаги от предположений, а критерии приёмки связывайте с наблюдаемым результатом. Это примеры применения навыка, а не объявление следующего занятия.

После занятия можно отдельно изучить Codex CLI и gh, skills, FPF, MCP-подключения к таблицам или Telegram, Jira/Beads, субагентов, Hermes, RPA и локальные модели. На стороне заказчика сначала согласуют задачу, данные, права доступа, владельца результата и проверку; настройка интеграций не обязательна для этой практики.
